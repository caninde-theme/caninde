# Porting Canindé to a new app

Thanks for bringing Canindé to another app! A port is small: one mapping, one generator, one folder.

Before you start, read [SPEC.md](SPEC.md) (the rules of use) and skim [ROLES.md](ROLES.md) (the roles you will map). Then open an issue with the **New app port** template so nobody duplicates your work.

## 1. Create the package

```
packages/<app>/
├── README.md        how to install the theme in that app, with screenshots
├── mapping.json     optional: declarative role mapping (see the VS Code package)
└── <output files>   generated by your target (committed)
```

## 2. Write a target

A target is a module in `build/targets/<app>.mjs` that exports an `id` and an async `build()` function. `build()` receives the resolved colors for one variant and returns the files to write:

| Argument | What it is |
| --- | --- |
| `root` | Absolute path of the repository |
| `variantId` | `"dark"`, `"light"`… |
| `variant.label` / `variant.type` | `"Canindé"` / `"dark"` |
| `variant.roles` | Map of role to `#RRGGBB`, for example `variant.roles["bg.base"]` |
| `palette` / `essence` | The generated palette and the raw essence, if you need them |

Return `[{ path, content }]`, where `path` is relative to the repository root. Generated files must start with a "do not edit" notice when the format allows comments.

If your app needs an alpha value, use `colorFor("accent.primary@35", roles)` from `build/lib/resolve.mjs`, which returns `#RRGGBBAA`.

### Example: Alacritty

```js
// build/targets/alacritty.mjs
export const id = 'alacritty';

const names = ['black', 'red', 'green', 'yellow', 'blue', 'magenta', 'cyan', 'white'];
const cap = (s) => s[0].toUpperCase() + s.slice(1);

export async function build({ variantId, variant }) {
  const { roles } = variant;
  const normal = names.map((n) => `${n} = "${roles[`ansi.${n}`]}"`).join('\n');
  const bright = names.map((n) => `${n} = "${roles[`ansi.bright${cap(n)}`]}"`).join('\n');

  const content = `# ${variant.label}: GENERATED by \`npm run build\`. Do not edit.
[colors.primary]
background = "${roles['bg.base']}"
foreground = "${roles['fg.default']}"

[colors.cursor]
cursor = "${roles['accent.secondary']}"
text = "${roles['bg.base']}"

[colors.selection]
background = "${roles['bg.hover']}"
text = "${roles['fg.default']}"

[colors.normal]
${normal}

[colors.bright]
${bright}
`;

  return [{ path: `packages/alacritty/caninde-${variantId}.toml`, content }];
}
```

## 3. Register it

In `build/index.mjs`, import your target and add it to the `targets` array:

```js
import * as alacritty from './targets/alacritty.mjs';
const targets = [vscode, alacritty];
```

## 4. Verify

```bash
npm run verify     # build, contrast check and tests
```

Then try the result in the real app, with real content, and compare it against the VS Code theme side by side.

## 5. Checklist for your pull request

- [ ] Only **roles** are used. No raw hex in the mapping or target
- [ ] Every ANSI color and the basic surfaces (background, foreground, cursor, selection) are mapped
- [ ] The rules in [SPEC.md](SPEC.md) §3 hold: gold cursor, italic comments, blue status/primary actions, red only for errors
- [ ] `npm run verify` passes and generated files are committed (never edited by hand)
- [ ] `packages/<app>/README.md` explains installation and has at least one screenshot
- [ ] The app table in `README.md` and `README.en.md` is updated

## Missing a role?

If the app needs something no role covers (for example a "diff gutter" color), do not hardcode it. Open an issue proposing a new role (see SPEC §8). Until it lands, map the closest existing role and note it in your PR.
